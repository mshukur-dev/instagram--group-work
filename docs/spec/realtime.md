# Realtime (Socket.IO)

Требования: `DM-3`, `DM-5`…`DM-7`, `NOTIF-2`, `CALL-3`, `CALL-5` в [TZ.md](../TZ.md).

## 1. Подключение

```
1. Фронт: GET /api/auth/socket-token → { token }  (JWT на 1 минуту)
2. Фронт: io(NEXT_PUBLIC_SOCKET_URL, { auth: { token } })
3. API (ChatGateway.handleConnection): проверяет token, кладёт userId в socket.data,
   добавляет сокет в комнату user:<userId>
4. При переподключении фронт снова берёт свежий token (callback в auth)
```

**Зачем отдельный токен:** сокет подключается напрямую к API (минуя прокси Next.js), поэтому httpOnly cookie с домена фронта туда не попадёт. Короткий токен из REST решает это безопасно.

Соединение одно на вкладку, создаётся после входа и закрывается при выходе. На фронте сокет живёт в `lib/socket.ts`, события подписываются в хуках.

## 2. Комнаты

| Комната | Кто в ней | Для чего |
|---|---|---|
| `user:<userId>` | все вкладки пользователя | личные события: новое сообщение, уведомление, входящий звонок |

Сообщения в переписке рассылаются по комнатам `user:<id>` **каждого участника**, а не по комнате переписки. Так новое сообщение приходит, даже если чат сейчас не открыт: обновляется список чатов и счётчик непрочитанных.

## 3. События

Все имена и типы событий лежат в `packages/shared/src/socket-events.ts` и используются и фронтом, и бэком. Писать имена строками напрямую нельзя.

### Сервер → клиент

| Событие | Данные | Когда |
|---|---|---|
| `message:new` | `Message` | новое сообщение в любой моей переписке |
| `message:deleted` | `{ conversationId, messageId }` | сообщение удалено |
| `message:reaction` | `{ conversationId, messageId, reactions }` | изменились реакции |
| `conversation:updated` | `ConversationPreview` | переименование, новый аватар, участники |
| `conversation:read` | `{ conversationId, userId, lastReadAt }` | кто-то прочитал переписку (для «Прочитано») |
| `typing` | `{ conversationId, userId, isTyping }` | кто-то печатает |
| `presence` | `{ userId, isOnline, lastSeenAt }` | собеседник появился в сети или вышел |
| `notification:new` | `Notification` | новое уведомление |
| `call:incoming` | `{ call, conversation, caller }` | мне звонят (1 на 1) или в группе начался звонок |
| `call:updated` | `{ callId, conversationId, status, participants }` | кто-то подключился/вышел, звонок принят |
| `call:ended` | `{ callId, conversationId }` | звонок завершён / отклонён / пропущен |

### Клиент → сервер

| Событие | Данные | Что делает сервер |
|---|---|---|
| `typing` | `{ conversationId, isTyping }` | проверяет участие, пересылает остальным участникам |
| `presence:subscribe` | `{ userIds }` | отвечает текущими статусами, дальше шлёт `presence` при изменениях |
| `presence:focus` | `{ focused }` | запоминает, активна ли вкладка — от этого зависит, слать ли Web Push (см. [push.md](./push.md)) |

### Как отправляется сообщение

Отправка — **обычным REST-запросом**, Socket.IO используется только для **доставки** другим:

```
Отправитель                    API                         Получатели
  │ POST /conversations/:id/messages                            │
  │─────────────────────────────►│ 1. проверка прав, валидация │
  │                              │ 2. сохранение в БД          │
  │◄──────── 201 Message ────────│ 3. socket message:new ─────►│ мгновенно
  │                              │ 4. Web Push тем, у кого     │
  │                              │    вкладка закрыта/в фоне   │
```

На фронте сообщение показывается **сразу** (оптимистично, с серыми часиками), после ответа сервера — как отправленное, при ошибке — с красной кнопкой «повторить». Для пользователя это выглядит так же мгновенно, как отправка через сокет.

Почему так: REST проще писать, отлаживать (видно во вкладке Network) и валидировать; ответ однозначно говорит, сохранилось ли сообщение. По нагрузке разницы для нашего масштаба нет.

## 4. Онлайн-статус

- Сервер считает число сокетов на пользователя (в памяти процесса). 0 → 1: пользователь в сети. 1 → 0: обновляем `User.lastSeenAt` и рассылаем `presence` с `isOnline: false`.
- Статус шлётся только тем, кто общается с пользователем в директе.
- Если у пользователя выключено `showActivityStatus`, его статус никому не отправляется.
- Хранение в памяти работает, пока API — один процесс. Для учебного проекта этого достаточно.

## 5. Отправка из сервисов

Сервисы не работают с сокетами напрямую. Есть `RealtimeService` с методами вроде `emitToUser(userId, event, data)` и `emitToUsers(userIds, event, data)`. Например, `MessagesService.send()` сохраняет сообщение в БД, а затем вызывает `realtime.emitToUsers(memberIds, 'message:new', message)`.

## 6. Фронтенд: как события попадают в UI

События **обновляют кэш TanStack Query**, а не отдельный стор:
- `message:new` → дописать сообщение в кэш `['messages', conversationId]`, поднять переписку наверх в `['conversations']`, увеличить счётчик непрочитанных.
- `notification:new` → дописать в `['notifications']`, увеличить `['notifications', 'unread']`.
- `call:incoming` → положить звонок в Zustand-стор `useCallStore` (это UI-состояние: показать окно входящего звонка).
